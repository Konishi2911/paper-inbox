# Paper Inbox 全体設計

## 目的

研究中に発見した文献を少ない操作で蓄積・整理・検索・引用する、ローカルファーストのデスクトップアプリ。Rust/GUIの学習も目的だが、実用性・保守性を優先する。設計方針と実装状況は区別し、工程は[roadmap](roadmap.md)、判断の根拠は[decisions](decisions.md)で管理する。

## 現在の責務分担

| クレート | 責務 | 持ち込まない依存 |
| --- | --- | --- |
| `paper-core` | ドメインモデル、更新・同一性判定、引用キー、BibTeX、command/query、ports | Slint、SQLite、HTTP実装 |
| `paper-storage` | SQLite、移行、検索、改訂・候補・版、ローカルイベント | GUI |
| `paper-metadata` | Crossref/arXivの固定HTTPS取得、応答検証、出典への変換 | UI状態、直接の保存 |
| `paper-desktop` | フォームとアプリケーション処理、Slint接続、ワーカー、設定 | GUI型のcoreへの流出 |

引き継ぎ案には `paper-metadata` がないが、既に実装済みであり、その境界を維持する。トレイトは保存・取得など交換する境界に絞る。

## 文献・版・出典

`Paper` は研究成果を、`PaperVersion` は各版を表す。出版社版（Version of Record）を正規とする方針だが、発見しただけでは切り替えず承認提案を作る。プレプリントの暫定利用と、出版社版発見後の項目更新は分離する。異なるDOIや関連版を同一文献へ自動統合しない。

手動情報と外部候補を出典付きで区別する。候補は明示した提示項目だけを対象とし、省略を削除として扱わない。初回未入力には手動改訂を作らず、明示的クリアには手動改訂を作る。情報源・レコード・更新日時・現在の項目headを使って更新を判定し、取得日時だけで新旧を決めない。手動値、削除提案、鮮度不明、競合は承認対象。古いheadに対する採用は拒否する。

候補IDと同じ文献・同じ内容の再投入はno-op、異なる内容や文献への再利用はエラー。識別子一致を確認できない候補は保留し、ユーザーの明示的な関連付け後も差分を項目別承認へ回す。正規版pointerと文献の書誌項目を同時に無条件で置き換えない。

詳細は[同一性](identity-assessment.md)、[候補と版](metadata-candidates.md)、[取得・引用キー](metadata-lookup-and-keys.md)を参照する。

## 永続化の現状

書誌情報は正規化SQLのみ。`bibliographies`、`contributors`、`keywords`、`paper_snapshots`、`papers`、`revisions`、`revision_parents`、`field_heads`、`events`、`event_parents`、版・候補・提案の各テーブルを使用する。想定案の `field_revisions` / `active_field_revisions` / 独立 `outbox` を名前だけ合わせて導入しない。未送信状態は現在のeventsの列で管理する。

SQLite schema version 5。文献と改訂の不変スナップショットを保持し、一括保存では文献全体と全headをトランザクション内で照合する。書誌変更、履歴、現在head、イベントは一緒にコミットし、失敗時は全体を戻す。論理削除後も引用キーの一意性を維持する。

検索はタイトル・著者・引用キーの部分一致、フィルタ、安定ソート、50件ずつ追加読込する連続スクロール（描画の仮想化は未実装）。現在はFTS5も全文索引もなく、日本語トークナイズは未確定。詳細は[保存契約](storage-contracts.md)。

## 添付と全文検索

添付（PDF）の方針は2026-11-17にユーザーが確定した（[決定](decisions.md)）。ファイルはDBへ入れず、内容のSHA-256を名前にして `library-files/blobs/<先頭2桁>/<64桁>` に置き、DBには参照行（attachments表）だけを持つ。書込は `tmp/` の一時ファイルへ書いてfsyncしてからrenameするので、途中で止まっても完全なファイルか削除可能な `.part` だけが残る。同一内容は1つの実体を共有する。DB行の追加はファイルの配置後に行い、DBに行があるのにファイルがない状態を作らない。逆に行のないファイル（孤立）は起こり得るため、利用者が「未使用PDFの整理」を実行したときだけ削除する。添付を外してもファイルは消さず、行に外した時刻を記録する（履歴を保つ）。読込時にハッシュを再計算し、不一致は破損として報告する。

実装済みは保存層（`FileBlobStore`、attachments表、`AddAttachment`/`RemoveAttachment`、イベント、検索の添付有無）とアプリ層（`apps/desktop/src/attachment.rs`）まで。UI（詳細画面のPDF欄、「未使用PDFの整理」画面）は[UI設計](ui-design.md)のA3を参照。型・ポートの存在と保存/UIの実装済みを混同しない。

アプリ層の取り決め:

- 取り込みは先頭1024バイト内の `%PDF-` を確認してから保存する。PDF以外はファイルも行も残さない。上限は512 MB。
- 保存→行の追加は一つのロック内で行う。「未使用PDFの整理」は同じロック内で未使用集合を再計算するため、取り込み中のファイルは消えない。
- 同じ文献への同一PDFの再添付は拒否し、別の文献へは同じ実体を共有する。
- 開くときは元のファイル名で一時フォルダー（既定はOSの一時フォルダー配下）へコピーする。Windowsで使えない文字は`_`にし、予約名には`document-`を付け、`.pdf`を保証する。コピー中にハッシュを検証し、不一致なら一時コピーを削除して開かない。
- OSへの引き渡しはシェルを介さず `explorer.exe` / `open` / `xdg-open` に1引数で渡す。起動時に24時間より古い一時コピーだけを削除する（別のアプリ起動や開いているビューアのファイルを消さないため）。
- 保存先は`library.sqlite`と同じフォルダーの`library-files/`（`Config::files_dir`）。

全文検索はFTS5等を候補とし、書誌検索・PDF抽出・索引更新の責務、日本語検索を評価してから決定する。

## 同期の将来方針

Gitに着想を得た履歴・イベントを使うが、通常操作としてpush/pullを要求しない。オフラインで利用し、接続回復後は自動同期、判断が必要な競合のみ通知する。独立変更は自動統合し、競合は双方を保持して提案する。

遠隔適用は冪等、依存イベント欠落は保留、遠隔適用の再送信ループを防止し、因果関係を端末時刻だけに依存させない。現在はローカルの端末sequence・親イベント・未送信状態のみで、遠隔transport/applyは未実装。端末間因果依存、削除競合、タグ集合、プロトコル、サービス、圧縮/GCは未確定で、実装前に判断する。
